既存のReactコンポーネントを、
[web-tasuke:react-component-convention](../react-component-convention/SKILL.md)スキルが定める規約に沿ってリファクタリングします。
規約の詳細はそのスキルにあるので、点検を始める前に読んでください。

# 対象

以下の引数が、対象のファイルパスまたはコンポーネント名です。

```text
$ARGUMENTS
```

引数が無い場合は、IDEで開いているファイルか、ユーザーが直前に話題にしたコンポーネントを対象にします。
対象のコンポーネントと同じファイルに同居している関連コンポーネントも、合わせて対象にします。

対象のファイルを読みます。
ファイル名から責務が分からない場合は、そのコンポーネントをimportして使っている箇所も読みます。

# 違反の洗い出し

以下の観点で対象を点検し、違反している箇所を列挙します。

- 構造の順序: import、デザイン定義、props定義、コンポーネントの順になっているか。
- 1ファイル1コンポーネント: ファイルの中のコンポーネントは1つだけか。
- ファイル名: 新しく作るファイルや大幅に書き換えるファイルの名前が、`index.tsx`や`index.ts`になっていないか。
- 肥大化: 関数の冒頭から最初のJSX(`return`の直前)までが肥大化していないか。
- 肥大化: 重複する構造、深い条件分岐、JSXの手前で用意する変数の多さ、
  複数のドメイン概念の混在といった読みづらさが、JSXにないか。

web-tasukeプラグインの他のスキルが定めるTypeScriptの規約に違反していないかも確認します。

# 計画の提示

編集を始める前に、何をどう変えるつもりかを箇条書きでユーザーに示して、合意を取ります。
以下を含めます。

- 切り出すカスタムフックと子コンポーネント、それぞれのファイル名
- 元のファイルの最終的な構成(デザイン定義、props定義、コンポーネントの配置)
- ファイル名を変える場合は、変更前と変更後のファイル名の対応

フックやファイルの名前の好み、分割の粒度など、ユーザーの方針で決まる点があれば、
ここで`AskUserQuestion`を使って確認します。

# 編集

合意が取れたら編集します。
途中で壊れにくいように、以下の順に進めます。

- カスタムフックや子コンポーネントなど、切り出し先のファイルを新しく作る。
- 元のファイルから切り出した実装を取り除き、新しいファイルからimportする。
- 元のファイルを、デザイン定義、props定義、コンポーネントの順に整える。
- ファイル名を変える場合は、最後に`git mv`で変えて、そのファイルをimportしている箇所を全て更新する。

# 検証

プロジェクトのリンターとビルドを実行して、壊していないことを確かめます。
コマンドは、以下のように、このスキルで許可されている形を先頭に置いて実行します。

- パッケージマネージャのスクリプトは、`pnpm lint`のような省略形ではなく、
  `pnpm run lint`のように`run`を付けて実行します。
- `nix build`と`nix-fast-build`は`--no-link`を最初の引数にして、
  リポジトリの中に`result`のシンボリックリンクを作らないようにします。
  `--out-link`と`-o`は指定しません。
- `tsc`は`--noEmit`を最初の引数にして、コンパイル結果をリポジトリの中に書き出さないようにします。
- `biome`は`check`、`format`、`lint`のいずれかのサブコマンドで実行します。

エラーが出た場合は、原因を読み取って根本から直します。
`// eslint-disable-next-line`や`as any`で回避するのは、ユーザーに相談して了承を得た場合だけです。

# 報告

最後に、以下を簡潔にユーザーへ報告します。

- 検出した違反と、それぞれへの対応
- 新しく作ったファイル、名前を変えたファイル、削除したファイル
- リンターとビルドの結果
- 動作確認が必要な箇所。
  リファクタリングなので振る舞いは変わらない想定ですが、念のため確認してほしい点を伝えます。

# 守ること

- 振る舞いは変えません。
  バグ修正、仕様変更、最適化は、明示的に指示された場合だけ行います。
- 規約に定められていない例外を、自分の判断で認めません。
  例外にせざるを得ない場合は、ユーザーに確認します。
- 将来の必要を見越した抽象化はしません。
  今あるコードに対して必要な最小限の分割だけを行います。
- `sva`やPanda CSSのトークンなど、既存の命名規約とデザイントークンは変えません。
- 切り出しによって、importの循環参照やファイル間の責務の逆流が起きないようにします。
