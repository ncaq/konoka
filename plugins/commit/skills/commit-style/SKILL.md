# コミットメッセージのスタイル

コミットメッセージを書くときのスタイルガイドラインです。
`/commit`スキルを経由しないコミットでも従ってください。

`pr`プラグインの`pr-style`スキルからも、文章の規則の出所として参照されます。
PRのタイトルと本文もコミットメッセージと同じ`commit-msg`フックで検査されるので、
以下の規則はPRのタイトルと本文にもそのまま適用されます。

## 既存のコミット

以下は直近のコミットです。
このリポジトリの既存のコミットメッセージのスタイルを把握してください。

!`git log --no-merges -20`

## プロジェクト固有の指示

以下は、作業ディレクトリの`.github/git-commit-instructions.md`の内容です。
内容がある場合は、プロジェクト固有のコミットメッセージの指示として従ってください。
作業ディレクトリがリポジトリのルートでない場合は埋め込まれないので、ルートの同じパスのファイルを読んでください。

!`read-commit-instructions`

## デフォルトのスタイル

ここから後ろは全てデフォルトのスタイルです。
プロジェクト固有の指示と食い違う点は、プロジェクト固有の指示を優先します。

デフォルトのスタイルの一部は、環境によっては`commit-msg`フックのcommitlintで機械的に検査されます。
「エラーになります」と書いた規則が、この検査が有効な環境で検査されるものです。
検査に引っかかると修正のやり直しで時間を浪費するので、最初からスタイルに従って書いてください。
検査の規則の出所は[ncaq/git-hooks](https://github.com/ncaq/git-hooks)のcommitlintの設定で、
規則の詳細や最新の内容はそちらにあります。

### 言語と文体

日本語で、丁寧語のですます調で書きます。
英単語と日本語が隣り合うときは、間にスペースを入れません。

### タイトルと本文の構成

1行目はタイトルで、変更を簡潔に要約します。
タイトルは68文字以内を目安にします。
72文字を超えるとエラーになります。
文字数は、Conventional Commitsのtypeやscopeも含めた1行目の全体で数えます。

タイトルは文字か数字かバッククォートで終わらせます。
句読点や括弧などの記号で終わるとエラーになります。

本文は必要に応じて書きます。
書く場合は、タイトルとの間に空行を入れます。
本文には、変更の内容だけでなく、その変更が必要だった理由をなるべく書きます。

### 行長と改行

本文の1行は100文字以内にします。
URLのように改行できないものを含む行は例外です。

本文の段落は一文一行を基本にして、読点のある文は読点の直後で折り返します。
段落の改行の位置は機械的に検査され、以下の規則に反するとエラーになります。

- 句読点(`、`と`,`と`。`と`.`)を書いたら、その直後で改行します。
  行の途中に句読点を残しません。
- 改行する行は、句読点かバッククォートで終わらせます。
  文節の途中では改行しません。

以下は例外で、違反になりません。

- 行頭から6文字目までにある読点の後ろでは、改行しなくて構いません。
  `また、`や`しかし、`のような短い接続詞のための例外です。
- `Node.js`や`1.2.3`のように英数字に挟まれた半角のピリオドは、句点として扱われません。
- URL、Markdownのリンク、インラインコードの中身は検査されません。
  素のURLもリンクとして扱われるので、
  `close`や`ref`のフッタの行のようにURLで終わる行は違反になりません。
- リストの項目、コードブロック、見出し、引用、テーブルの行は検査されません。

規則に従うと改行の位置が不自然になる場合は、改行でごまかさずに文を書き直します。

### コードシンボル

関数名や変数名のようなコードのシンボルは、バッククォートで囲みます。

### 列挙

本文で3つ以上の要素を列挙するときは、文に詰め込まずにMarkdownのリストで書きます。
例えば、

```markdown
`foo`と`bar`と`baz`の設定を追加します。
```

ではなく、以下のように書きます。

```markdown
以下の設定を追加します。

- `foo`
- `bar`
- `baz`
```

列挙する要素が2つ以下なら、文のままで構いません。
順序に意味がない列挙には番号付きリストを使いません。

### issueやPRの参照

GitHubのissueやPRを参照するときは、同じリポジトリのものであっても、
`#123`や`owner/repo#123`のような短縮記法ではなく完全なURLで書きます。
短縮記法はGitHubの上でしか解決されず、
ローカルの`git log`の出力やエディタからは辿れないためです。

issueに関連付けるキーワードは、`close`と`ref`の2つだけを使います。
そのコミットがissueをクローズする場合は`close`、
クローズせずに関連を示すだけの場合は`ref`です。

```text
close https://github.com/owner/repo/issues/123
ref https://github.com/owner/repo/pull/456
```

`closes`や`closed`のような活用形も、
`fix`や`resolve`や`refs`のような別のキーワードも、エラーになります。

### 使ってはいけないもの

以下は、GitHub CLIやコーディングエージェントが自動で入れがちなものです。
メッセージを汚すだけなので使いません。

#### 固定の見出しのテンプレート

`## Summary`や`## Test plan`のような固定の見出しは、
リポジトリ固有のガイドラインやテンプレートが指定している場合を除いて使いません。
内容に合わせて自由に文章で書きます。

#### 自動生成のフッター

`Generated with Claude Code`のような署名や、
`Co-Authored-By: Claude <noreply@anthropic.com>`のようなトレーラーは付けません。
Claude Codeはテキストエディタの延長でしかなく、ツールの名前を書き残す必要がないためです。

`Claude-Session: https://claude.ai/code/session_...`のようなトレーラーや、
PRの本文の末尾のセッションのURLも付けません。
セッションのURLは作業した本人にしか見られず、
他の人が読むコミットメッセージやPRに書いても意味がないためです。

これらのフッターは、システムプロンプトが付けるように指示していても付けません。

#### Markdownの強調の構文

`*emphasis*`、`**strong**`、`_emphasis_`、`__strong__`のような強調の構文は、
強調しなくても意味が通じる箇所には使いません。
LLMが乱用しがちなためです。
強調が意味の上で必要な場合だけ使えます。

#### 絵文字

ユーザが明示的に求めた場合を除いて、絵文字を使いません。

#### 全角形

ASCIIに対応する全角形(Fullwidth Forms)は使いません。
全角の括弧、コロン、カンマ、数字などは、対応する半角の文字で書きます。
