---
name: commit
description: Generate a commit message from staged changes, then let the user review before committing in manual mode or commit without confirmation in auto mode. Use when the user wants to commit changes or create a git commit.
argument-hint: "[manual|auto]"
allowed-tools: >-
  Bash(commit-prepare:*),
  Bash(git commit:*),
  Bash(git diff:*),
  Bash(konoka-commit-editor:*),
  Bash(run-commit-msg-hook:*),
  Bash(show-staged-patch:*),
  Edit,
  Read,
  Skill(commit:commit-style),
  Write
effort: low
---

Gitリポジトリの変更をコミットします。
差分からコミットメッセージを生成して`commit-msg`フックで検査し、
`manual`確認モードではユーザの確認を取ってから、
`auto`確認モードでは確認を取らずにコミットします。

# 確認モード

引数の`$ARGUMENTS`を確認モードとして解釈します。

- `manual`: 差分とコミットメッセージをユーザに見せて、確認を取ってからコミットします。
- `auto`: 差分の表示と確認を省き、コミットメッセージを提示してそのままコミットします。

引数が空の場合は`manual`です。
`manual`とも`auto`とも解釈できない値の場合も`manual`として扱い、
解釈できなかった値を完了報告で伝えます。
確認を省くのは、`auto`と明示された場合だけにするためです。

# コミットの準備

!`commit-prepare`

上は、このスキルの読み込み時に`commit-prepare`を実行した出力です。
`commit-prepare`は、ステージ済みの変更があればそれだけをコミットの対象にします。
ステージ済みの変更が1つも無ければ、全ての変更を`git add --all`でステージして対象にします。
成功すると、以下のキーを持つJSONを1行で出力します。

- `editmsgPath`: コミットメッセージを書き込むファイルのパスです。
  以降はメッセージファイルと呼びます。
  このファイルはまだ作られていません。
- `patchPath`: ステージされた差分を書き出したファイルのパスです。
  以降はパッチファイルと呼びます。

プラグインの導入や更新の直後は、ビルドのログが前に付くことがありますが、JSONの行が結果です。

このJSONが得られていない場合は、準備に失敗しています。
コミットする変更が無い場合もこの失敗になります。
出力されている内容を報告して、終了してください。

以降のコマンド例の`<editmsgPathの値>`と`<patchPathの値>`は、JSONの値に置き換えて実行します。

# コミットメッセージの生成

`Skill`ツールで`commit:commit-style`スキルを呼び出し、そのスタイルガイドラインに従います。

`Read`ツールでパッチファイルを読んで変更の内容を把握し、コミットメッセージを生成します。
生成したコミットメッセージを、`Write`ツールでメッセージファイルに書き込みます。
メッセージファイルにはコミットメッセージだけを書きます。
差分を書くと、差分までコミットメッセージとして検査され、コミットされてしまうためです。

# コミットメッセージの検査

以下のコマンドで検査します。

```bash
run-commit-msg-hook <editmsgPathの値>
```

`git commit`が起動するのと同じ`commit-msg`フックで、メッセージファイルを検査するコマンドです。
失敗した場合は、出力された指摘に従ってコミットメッセージを直して、再実行します。
3回直しても検査を通らない場合は、どちらの確認モードでも、
指摘の内容をユーザに報告して指示を仰ぎます。

フックはメッセージファイルを書き換えることがあります。
検査を通ったら`Read`ツールでメッセージファイルを読み直し、
以降はその内容をコミットメッセージとして扱います。

# 差分の表示

`manual`の場合だけ行います。

コミットメッセージの確認の直前に、以下のコマンドでステージされた差分をユーザに見せます。

```bash
show-staged-patch <patchPathの値>
```

差分はこのコマンドの出力だけで見せます。
自分の文章として差分を出力し直さず、要約や説明も付けずに、コミットメッセージの確認へ進みます。
差分の全文を出力し直すと時間がかかり、
差分の中にコードフェンスがあるとMarkdownの表示が壊れるためです。

# コミットメッセージの確認

`manual`の場合だけ行います。

`AskUserQuestion`ツールで、コミットメッセージの扱いをユーザに確認します。
質問文には、コミットメッセージの全文を、要約も省略もせずに含めます。
ユーザがその内容を見て判断するためです。

選択肢には以下の2つを設定します。

- このままコミットする(Recommended): コミットメッセージをそのまま使ってコミットします。
- テキストエディタで編集する: エディタでコミットメッセージを編集してからコミットします。

## このままコミットする場合

コミットの実行へ進みます。

## テキストエディタで編集する場合

以下のコマンドを、タイムアウトを最大の600秒(10分)に設定して実行します。
ユーザが編集している間はコマンドが終了しないためです。

```bash
konoka-commit-editor <editmsgPathの値> <patchPathの値>
```

コマンドが成功した場合は、`Read`ツールでメッセージファイルを読み直します。
誤字があれば直して上書きし、直した箇所を完了報告で伝えます。
続けて`run-commit-msg-hook`でもう一度検査します。
ユーザ自身が書いた内容なので、検査に失敗しても書き換えずに、
指摘の内容を報告して指示を仰ぎます。
検査を通ったらコミットの実行へ進みます。

コマンドが失敗した場合は、ユーザがコミットを取りやめたものとして扱い、
コミットせずに終了します。
エディタを起動できなかった場合も同じ失敗になるので、
終了の報告にはコマンドのエラーメッセージを含めます。

## 自由入力の場合

`AskUserQuestion`ツールは、自由入力の選択肢(`Other`)を自動で追加します。
`Other`に入力された文章は、コミットメッセージへの修正指示として扱います。
`Edit`ツールでメッセージファイルを修正指示の通りに直し、
コミットメッセージの検査をやり直してから、コミットメッセージの確認に戻ります。

## キャンセルされた場合

選択がキャンセルされた場合は、ユーザがコミットを取りやめたものとして扱い、
コミットせずに終了します。

# コミットメッセージの提示

`auto`の場合だけ行います。

以下のコマンドで、コミット対象のファイルの一覧を表示します。

```bash
git diff --cached --stat
```

続けて、コミットメッセージの全文を、要約も省略もせずにテキストとして出力します。
`AskUserQuestion`ツールは呼び出さず、ユーザの応答も待たずに、コミットの実行へ進みます。

確認は取りませんが、コミットする内容は`manual`と同じくコミットの前に見えるようにします。
ファイルの一覧も出すのは、コミットメッセージが生成した要約であり、
意図せずステージされたファイルにはファイルの一覧でしか気付けないためです。
確認を求めないので、差分の全文は表示しません。

# コミットの実行

以下のコマンドでコミットします。

```bash
git commit -F <editmsgPathの値>
```

検査を通ったメッセージファイルをそのままコミットに使うために、`-F`で渡します。
`-m`でコミットメッセージを渡し直すと、検査した内容と食い違う恐れがあります。

# 完了報告

コミットの結果を報告します。
コミットメッセージの全文は既に提示しているので、繰り返す必要はありません。
コミットに失敗した場合は、`git commit`の出力を添えて報告します。
